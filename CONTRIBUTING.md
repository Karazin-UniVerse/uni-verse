# Git Flow & Contributing Guidelines

Цей документ визначає стандарти розробки, структуру гілок та регламент релізів у проєкті **UniVerse**.

---

## 1. Структура гілок (Branching Strategy)

- **`main`** (Production / Stable):
  - Стабільна релізна гілка.
  - Прямий пуш суворо заборонено (`Protected Branch`).
  - Зміни потрапляють **виключно через релізні Pull Requests із гілки `develop`** після проходження стабілізації (Code Freeze) та тестування на Stage.
  - Захист: Ruleset `Main Protection` (мінімум 2 схвалення, блокування force push, заборона видалення).

- **`develop`** (Integration / Stage):
  - Основна робоча гілка для щоденної інтеграції функціоналу команди.
  - Код з `develop` автоматично розгортається на **Stage-стенд** для перевірки.
  - Прямий пуш заборонено (`Protected Branch`). Усі зміни — тільки через Pull Request.
  - Захист: Ruleset `Develop` (мінімум 1 схвалення, обов'язковий зелений CI `quality` та `Verify Code Freeze Status`, блокування force push, заборона видалення).

- **Робочі гілки розробників**:
  - `feature/<назва-фічі>` — розробка нового функціоналу (відгалужується від `develop`).
  - `fix/<опис-бага>` — виправлення виявлених дефектів (відгалужується від `develop`).
  - `refactor/<модуль>` — рефакторинг та оптимізація існуючого коду.
  - `chore/<задача>` — оновлення конфігурацій, CI, залежностей або документації.
  - `hotfix/<назва>` — термінові патчі для Stage/Production або байпас під час Code Freeze.

---

## 2. Регламент Pull Request та Code Review

1. **Цільова гілка**: усі робочі PR відкриваються виключно в гілку **`develop`**.
2. **Критерії успішного злиття (Merge Criteria)**:
   - Мінімум **1 схвалення (Approve)** від іншого члена команди.
   - Усі зауваження та діалоги рев'ю (`Conversations`) мають бути повністю переведені в статус **Resolved**.
   - Обов'язкове успішне проходження перевірок CI:
     - `quality` (успішне проходження `pnpm lint`, `pnpm typecheck`, backend coverage тестів та `pnpm build`).
     - `Verify Code Freeze Status` (перевірка відсутності блокування на злиття нових змін).
   - Актуальність гілки щодо останніх змін у `develop` (`Require branches to be up to date`).
3. **Конвенція комітів**:
   - Дотримуватися стандарту [Conventional Commits](https://www.conventionalcommits.org/):
     `feat: ...`, `fix: ...`, `refactor: ...`, `chore: ...`, `docs: ...`, `test: ...`.

---

## 3. Релізний цикл та процедура Code Freeze

Перед випуском стабільної версії у `main` команда дотримується чіткої послідовності кроків:

```
  [feature/* / fix/*] ──(PR + 1 Review)──> develop (Stage деплой)
                                               │
                                      [🧊 Code Freeze] ──(тестування на Stage)
                                               │
                                         (Release PR)
                                               ▼
                                             main (Production)
```

1. **Активація Code Freeze**:
   - Запускається GitHub Actions воркфлоу **`Toggle Code Freeze`** (вибирається дія `freeze`).
   - Воркфлоу встановлює репозиторний тег `code-freeze`.
   - **Результат**: перевірка `Verify Code Freeze Status` автоматично блокує кнопку `Merge` для всіх PR у `develop`. Вливання нових фіч тимчасово призупиняється.
2. **Тестування на Stage**:
   - Проводиться повне регресійне тестування розгорнутого стенду на Stage.
   - Якщо виявлено критичні баги, виправлення створюються з міткою (label) `hotfix` або `freeze-bypass` — такі PR мають дозвіл на проходження через Code Freeze.
3. **Реліз у `main`**:
   - Після підтвердження стабільності створюється релізний PR: `develop` -> `main`.
   - Вимагається мінімум 2 схвалення (Approve) та успішний прохід Quality Gate SonarCloud.
   - Виконується злиття (Merge / Squash) у `main`.
4. **Зняття Code Freeze**:
   - Запускається воркфлоу `Toggle Code Freeze` із дією `unfreeze` (тег `code-freeze` видаляється).
   - Гілка `develop` знову відкривається для злиття нових Pull Requests наступного спринту.
